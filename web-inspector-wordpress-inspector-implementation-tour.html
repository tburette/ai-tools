What is now available

There are now two independently usable skills. Web Inspector remains a generic Playwright renderer and interaction harness, but it now supports explicit persistent Chromium profiles, configuration, headed sessions, and two new generic actions. WordPress Inspector is a new read-only adapter that uses Web Inspector to inspect an authenticated WordPress admin area and Gutenberg editor.

The boundary is intentional: browser mechanics remain generic in Web Inspector; WordPress URLs, selectors, classifications, and safety rules live in WordPress Inspector.

For users and agents

Existing Web Inspector captures are unchanged

Normal no-profile captures stay headless and ephemeral. Each viewport gets a fresh browser context and no state survives exit.

cd web-inspector
node scripts/capture_page.mjs http://localhost:3000/ \
  --viewport 1440x1100 \
  --output-dir /tmp/web-inspector/page

The usual screenshots and report.json are produced. Reports now also include headed, profile, and persistentContext.

Persistent login state is deliberate

Declare a Chromium profile in versioned configuration, then request it explicitly. The tool never infers a profile from a hostname, repository, or login page.

{
  "version": 1,
  "defaults": { "headed": false },
  "profiles": { "wp-local": { "browser": "chromium" } }
}
node scripts/capture_page.mjs http://example.test:8888/ \
  --profile wp-local \
  --config ~/.config/web-inspector/config.json \
  --output-dir /tmp/web-inspector/profile-check

Authenticate interactively, never on the command line

cd wordpress-inspector
node scripts/wordpress_inspector.mjs authenticate \
  --base-url http://example.test:8888 \
  --profile wp-local \
  --config ~/.config/web-inspector/config.json

This opens a dedicated visible Chromium window. An operator signs in there, closes it, and the command runs a read-only admin probe. It never accepts credentials as options, config, report fields, or process arguments.

Inspect WordPress without mutation

node scripts/wordpress_inspector.mjs check-admin \
  --base-url http://example.test:8888 \
  --profile wp-local \
  --config ~/.config/web-inspector/config.json \
  --output-dir /tmp/wordpress-inspector/admin

node scripts/wordpress_inspector.mjs check-editor \
  --base-url http://example.test:8888 \
  --profile wp-local \
  --editor-url 'http://example.test:8888/wp-admin/post.php?post=123&action=edit' \
  --output-dir /tmp/wordpress-inspector/editor

Each run produces a concise wordpress-summary.json, the generic report.json, and screenshots. Expected classifications include AUTHENTICATED, AUTH_REQUIRED, EDITOR_INVALID_BLOCKS, and TECHNICAL_ERRORS.

Two generic actions were added

ActionBehavior
assertNotVisibleFails when any matching element is visible during a short assertion window (250 ms by default).
clickIfVisibleClicks the first visible match and reports clicked: true; otherwise reports clicked: false.

Technical design

Configuration and state

Configuration precedence is --config, WEB_INSPECTOR_CONFIG, ${XDG_CONFIG_HOME}/web-inspector/config.json, then ~/.config/web-inspector/config.json. A missing file uses safe defaults; malformed configuration and undeclared profiles fail explicitly.

State precedence is WEB_INSPECTOR_STATE_DIR, ${XDG_STATE_HOME}/web-inspector/profiles, then ~/.local/state/web-inspector/profiles. Profile directories are owner-only where supported, symlinked directories are rejected, and lock errors are normalized without leaking paths.

Browser lifecycle

  • No profile: fresh ephemeral context per viewport.
  • Named profile: one persistent Chromium context, reused for the run and flushed on close.
  • Firefox: supported for ephemeral captures only.

Persistent browser state can include cookies, local storage, IndexedDB, and session state. It is a bearer credential and never belongs in a repository or ordinary temporary output directory.

WordPress classification and safety

WordPress Inspector first runs a short structural authentication probe. It can quickly return AUTH_REQUIRED without waiting through editor readiness timeouts. It separately records browser diagnostics, filtering expected action-failure entries so they do not become false technical errors.

Editor URLs are constrained to a same-origin, supported read-only route: post.php?action=edit&post=<positive-id> or site-editor.php without an action parameter. Cross-origin URLs, arbitrary admin routes, mutation endpoints, and duplicate action/post query parameters are rejected.

The adapter does not save, publish, trash, upload, install, activate, reset, or submit credentials. It may only dismiss a close control scoped to a known Gutenberg welcome guide.

Runtime and installation

WordPress Inspector invokes Web Inspector with process.execPath and argument arrays. In this source checkout it uses the sibling skill; a separately installed copy can set WEB_INSPECTOR_SKILL_DIR. Playwright is discovered from existing installations only—no npm install or browser download occurs implicitly. Headed sessions require a graphical display.

All checks passed. A subagent review was also completed, and its findings were incorporated: inherited profile lookup, config forwarding, permissions, auth-ordering, selector false positives, delayed/duplicate assertions, technical diagnostics, report failure handling, and editor-route safety.

Authorized local WordPress integration

  • The authorized network site’s admin check passed with AUTHENTICATED.
  • The Home editor and existing all-patterns review page both passed with AUTHENTICATED.
  • Each check returned HTTP 200, produced an inspected screenshot, and reported no console/page/request/response errors.
  • No mutation controls were exercised. A repeat all-patterns check left the observed post modification timestamp unchanged.

The local environment was started through its authorized command, but no files in that project were edited. Child/farm subsites were intentionally excluded from the authorized scope.

Limits and intentionally deferred work

  • No persistent Firefox profile, automatic profile selection, credential vault, automatic reauthentication, or profile deletion command.
  • No automatic resolution of WordPress posts, slugs, templates, or project-specific targets; callers provide an allowed editor URL.
  • No mutation testing, full accessibility auditing, visual diffs, video recording, or network mocking.
  • Multisite authentication remains host-specific: authenticate and check each separately authorized host explicitly.
  • Screenshots and reports may contain private admin information; keep them protected and out of commits.

For day-to-day browser work, read Web Inspector. For authorized WordPress administration and Gutenberg checks, read WordPress Inspector.
